## 1. 학습 게임의 동기부여 장치

### 1.1 Boot.dev (조사 완료)

| 항목 | 내용 | 근거 |
|---|---|---|
| XP·레벨 | 레슨(assignment)을 완료하면 XP를 얻습니다. 2024-05부터 XP 보너스가 레슨 난이도에 더 크게 좌우되도록 조정됐습니다. 레벨은 누적 XP로 자동 상승하고, 레벨이 높을수록 다음 레벨에 더 많은 XP가 필요합니다. 레벨 구간마다 이름(Sage, Archsage, Mage, Archmage 등)이 있습니다. 레벨이 열어 주는 기능은 **미확인**입니다. | [B4], [B1](추정) |
| 콘텐츠 진행 | 코스 → 챕터 → 레슨 구조입니다. 예를 들어 Python 코스는 15챕터, 168레슨, 30시간 분량입니다. 챕터·코스를 잠그는 조건은 공식 페이지에 명시되어 있지 않아 **미확인**입니다. 무료 모드에서는 읽기만 할 수 있고, 과제 제출과 퀴즈는 유료입니다. | [B7], [B8] |
| 스트릭 | 2024-03에는 **주간** 스트릭(한 주를 놓치면 초기화)이었고, 2024-11에 **일간**으로 바뀌었습니다. 레슨 완료나 GitHub 커밋이 하루 활동으로 인정됩니다. 보호 장치는 두 단계입니다: ① Ember는 그날 평소 이상으로 학습하면 1개 충전되고, 결석한 날 가장 먼저 소모됩니다. ② Frozen Flame은 젬으로 구매하며 4일을 보호하고, 가격이 비싼 편입니다. 설계 의도는 "주 5/7일이면 충분히 건강한 습관"이라고 밝히고 있습니다. | [B2], [B3], [B5], [B6] |
| 보상 | 화폐는 젬이고, 상자(loot box)가 있지만 소액결제는 없습니다. 2024-05부터 업적과 일일 퀘스트 보상을 XP·젬 대신 상자로 일원화했습니다. 상자는 일일 퀘스트, Sharpshooter spree, 보스 처치로 얻습니다. 아이템으로는 Potion(1시간 동안 XP +25%. 2024-12에 '30분 동안 +50%'에서 완화), Seer Stone, Baked Salmon, Frozen Flame이 있습니다. 그 밖에 업적, 프로필 히트맵, 코스 수료 인증서가 있습니다. | [B4], [B9], [B10], [B7] |
| 막혔을 때 | AI 튜터 Boots가 소크라테스식 질문으로 돕습니다. 해답을 보거나 Boots와 대화하면 XP 페널티가 있습니다. Seer Stone을 쓰면 해답을 봐도 XP를 잃지 않고, Baked Salmon을 쓰면 Boots와 대화해도 XP를 잃지 않습니다(공식 확인). 페널티 크기는 해답 보기가 레슨 XP의 100%, Boots 대화가 50%라는 자료가 있지만, 현재 404인 공식 위키의 검색 요약이라 **추정**입니다. | [B4], [B1] |
| 복습 | Training Grounds(2025-09)는 완료한 코스, 최근 학습 주제, 어려워한 주제, 경과 시간(spaced repetition)을 보고 맞춤 연습 문제를 만들어 줍니다. Spellbook은 완료한 레슨에 연결된 치트시트 페이지를 자동으로 열어 주고, 검색할 수 있습니다. | [B11], [B12] |
| 비판·부작용 | Boot.dev에 대한 공신력 있는 비판 자료는 **미확인**입니다. 다만 회사 스스로 Potion을 "너무 짧고 압박이 크다"는 이유로 완화했고, 보스전을 경쟁에서 협력으로 바꿨으며, 스트릭 기준을 "주 5/7일"로 완화했습니다. 이 세 가지는 압박을 줄이는 쪽으로 스스로 고친 사례입니다. | [B9], [B13], [B5] |

**PyRpg 시사점(잠정)**: 아래 내용은 Boot.dev 한 곳만 근거로 삼은 것이므로, 나머지 서비스 조사를 마친 뒤에 확정합니다.

- 스트릭 보호 장치를 '학습을 더 하면 자동으로 충전되는 보호'와 '골드로 사는 보호' 두 단계로 나누는 방식은 PyRpg에도 그대로 적용할 수 있습니다.
- 해답을 보면 보상이 0이 되는 방식은 design.md §5.3의 '해설서'와 같은 방향입니다.
- Boot.dev가 압박을 줄이는 쪽으로 여러 번 조정했다는 점은, 하루 15~30분을 오래 지속하려는 PyRpg의 목표와도 맞습니다.

**PyRpg 시사점(Codédex)**

- 레벨 상한(25)과 레벨 5단위 랭크 이름처럼 **"끝이 보이는" 레벨 구조**는 하루 15~30분 학습자에게 목표를 주기 좋습니다.
- "챕터 끝 체크포인트 프로젝트"는 PyRpg의 지역 보스전과 같은 역할입니다.
- "힌트가 모호하고 난이도가 갑자기 뛴다"는 비판은 PyRpg에서도 가장 피해야 할 이탈 원인입니다(힌트 단계화 필요).

### 1.3 CodeCombat

> 확인 방법: `codecombat.com`과 도움말 사이트는 프록시에서 차단됐습니다. 대신 CodeCombat 클라이언트가 오픈소스(코드 MIT, 아트 CC-BY. 단, 레벨 데이터는 비공개)라서 GitHub 저장소 `codecombat/codecombat`의 2026-10-01 커밋 `14b0407`을 받아 **소스 코드를 직접 읽었습니다**[CC7]. 따라서 공식 문서보다 정확한 '구현 그대로의 값'이지만, 서버 쪽 값(보상 크기, AI 크레딧 수, 가격)은 소스에 없어 따로 표시했습니다.

| 항목 | 내용 | 근거 |
|---|---|---|
| XP·레벨(랭크) | XP(`points` 필드)에서 플레이어 랭크(예전 이름 "player level")를 로그 함수로 계산합니다: `rank = floor(5 × ln((XP + 100) / 100)) + 1`. 역산하면 랭크 2에 23 XP, 5에 123, 10에 505, 15에 1,545, 20에 4,371, 25에 12,052, 30에 32,930 XP가 필요합니다(직접 계산). 즉 랭크 5 올리는 데 필요한 XP가 약 2.7배(e)씩 늘어나는 구조입니다. 레벨 하나의 XP 보상 크기는 서버 데이터라 **미확인**입니다. | [CC1] |
| 랭크가 열어 주는 것 | 장비 아이템마다 tier 값이 있고, 랭크별 tier 상한 표(`tiersByLevel`)로 "이 아이템을 쓰려면 필요한 랭크"를 계산합니다. 랭크가 부족한 아이템은 상점에서 **실루엣(잠김)**으로 보이고, 랭크가 되면 젬으로 구매합니다. CodeCombat에서 장비는 새 명령(메서드)을 주는 역할을 하므로(예: 이동 명령을 주는 부츠), 랭크가 곧 "쓸 수 있는 문법 도구"를 여는 셈입니다(장비=명령 관계는 **추정**: 소스의 `requiredProperties`(레벨을 풀려면 장착해야 하는 속성) 필드로 간접 확인). | [CC1], [CC6], [CC2] |
| 콘텐츠 진행·잠금 | 레벨마다 `requiresSubscription`(구독자 전용) 플래그가 있습니다. 레벨 종류는 demo/usage/mastery/advanced/practice/challenge로 나뉘고, 1~5 별점 난이도를 가집니다. 수업용 코스에서는 앞 레벨이 잠겨 있으면 다음 레벨로 넘어가지 않습니다(`isAnyPrecedingLevelLocked`). 무료로는 앞쪽 레벨 일부만 열리고, 개인 구독(월 $9.99, 매월 3,500 젬 지급)으로 나머지 레벨이 열린다는 자료가 있지만 가격·젬 수는 공식 페이지를 직접 확인하지 못해 **추정**입니다. | [CC2], [CC3], [CC8](추정) |
| 스트릭 | 받아 온 클라이언트 코드(app/core, lib, models, schemas, views/play)에서 'streak'라는 단어가 한 번도 나오지 않습니다. 스트릭 기능은 **없는 것으로 보입니다(추정)**. | [CC1] 저장소 검색 |
| 보상 | 화폐는 젬입니다. 레벨·업적으로 젬을 벌고 장비와 영웅을 삽니다. 업적 스키마의 보상(`RewardSchema`)은 영웅, 아이템, 레벨 해금으로 구성됩니다. `replayable` 레벨은 "난이도가 무한히 올라가며, 반복해서 깰수록 더 큰 보상"을 줍니다. 아레나(경쟁) 레벨에는 리더보드가 있습니다. | [CC2], [CC6] |
| 막혔을 때 ① 힌트 | 레벨마다 여러 개의 힌트 문서가 있고, 버튼으로 열고 넘길 수 있습니다. 힌트를 **10초 넘게 보면** '힌트 사용'으로 기록합니다(분석용). 힌트를 봐서 잃는 XP나 젬은 클라이언트 코드에서 찾지 못했습니다(→ **페널티 없음, 추정**). 힌트 문구는 A/B 테스트용 두 번째 세트(`hintsB`)까지 둡니다. | [CC4], [CC2] |
| 막혔을 때 ② AI 도움 | 'Ask AI' 도움은 크레딧제입니다. "기간(duration)당 남은 크레딧 수"를 보여 주고, 다 쓰면 기간이 지날 때까지 못 씁니다. 크레딧 수와 기간 값은 서버에서 내려와 **미확인**입니다. | [CC5] |
| 막혔을 때 ③ 연습 우회 | 가장 독특한 장치입니다. 레벨마다 `practiceThresholdMinutes`가 있어, 현재 레벨에서 보낸 시간이 이 값을 넘으면 다음 레벨 대신 **같은 개념의 연습(practice) 레벨로 안내**합니다(평가 레벨은 제외). 자동 생성 레벨의 기준값은 "원본 레벨 완료 시간 중앙값(p50)"에서 출발하고, 데이터가 없으면 `10초 + 5초 × (추가할 코드 줄 수)`, 그것도 없으면 2분으로 둡니다. 최솟값은 60초이며, 뒤 레벨로 갈수록 기준을 레벨당 10% + 10초씩 늘려 "느린 학생도 결국 다음으로 넘어가게" 합니다. 기본값은 5분입니다. | [CC3] |
| 복습 | 간격 반복 기능은 없습니다(**추정**: 소스에서 찾지 못함). 대신 ① 위의 연습 레벨 우회, ② 코스 중간·끝의 평가(assessment) 레벨(`middle`/`end`, 누적형 `cumulative` 포함), ③ 반복 가능한 레벨이 복습 역할을 합니다. | [CC2], [CC3] |
| 비판·부작용 | 리뷰 요약: ① 좋은 콘텐츠·레벨이 유료(구독 또는 젬)로 잠겨 있습니다. ② 난이도가 단계적으로 오르지 않고 갑자기 뛰는 구간이 있습니다. ③ 게임 요소가 학습 목표보다 눈에 띄어 "코딩을 배우는 건지 턴제 게임을 하는 건지" 모르겠다는 학부모 의견이 있습니다. ④ 초·중급 위주라 심화 학습에는 부족합니다. | [CC9](추정) |

**PyRpg 시사점(CodeCombat)**

- **시간 기반 연습 우회**(`practiceThresholdMinutes`)는 PyRpg에 바로 쓸 수 있는 장치입니다. "막혔다"를 힌트 요청이 아니라 **소요 시간**으로 감지하고, 벌을 주는 대신 더 쉬운 같은 개념 문제로 돌려보냅니다.
- 랭크 → 장비 → 새 명령 해금 구조는 "레벨이 오르면 쓸 수 있는 파이썬 문법(예: 딕셔너리, `collections.deque`)이 열린다"는 PyRpg 설정과 잘 맞습니다.
- 힌트에 페널티를 두지 않고 '10초 이상 봤는지'만 기록하는 방식은, 기록은 남기되 학습자를 벌하지 않는 좋은 기준점입니다.

**PyRpg 시사점(TwilioQuest)**

- **필수 = 레이저 장벽, 선택 = 보물상자** 구분은 PyRpg 맵 설계에 그대로 쓸 만합니다. 필수 문제만 진행을 막고, 심화 문제는 상자로 두어 하루 15분 학습자도 막힘 없이 진행하게 합니다.
- `assert` 메시지로 "무엇이 틀렸는지"를 알려 주는 채점 방식은, 코딩테스트처럼 통과/실패만 알려 주는 방식보다 초반 학습에 유리합니다. 다만 코딩테스트 대비라는 목표를 생각하면, 후반부에는 메시지를 줄여 실전 형식에 가깝게 가는 단계적 전환이 필요합니다.
- 보상 XP를 "일반 100 / 응용 300~400 / 보스 1,000"처럼 소수의 큰 덩어리에 몰아주는 배분은 지역 보스의 무게감을 만듭니다.

### 1.6 간격 반복 알고리즘

| 방식 | 핵심 규칙 | 근거 |
|---|---|---|
| Leitner 상자 | 1972년 독일 과학 저널리스트 Sebastian Leitner가 제안했습니다. 카드를 상자(칸)에 나눠 두고, **맞히면 다음 칸, 틀리면 첫 칸**으로 보냅니다. 뒤 칸일수록 복습 간격이 깁니다. 원래 방법은 날짜가 아니라 칸의 물리적 크기(1, 2, 5, 8, 14 cm)가 차면 복습하는 방식이었습니다. | [S1](추정) |
| Leitner 변형(Duolingo 기준선) | Duolingo 논문 코드의 Leitner 기준선은 반감기 `h = 2^(맞힌 횟수 −틀린 횟수)`일로 계산하고, 회상 확률은 `p = 2^(−경과일/h)`입니다. h는 15분~274일(9개월) 사이로 자릅니다. 즉 "한 번 맞히면 간격 2배, 한 번 틀리면 간격 절반"입니다(첫 칸 리셋보다 완만). | [S6] |
| SM-2 | 문항마다 반복 횟수 n, 쉬움 계수 EF(초깃값은 이번 조사에서 확인하지 못해 **미확인**), 간격 I를 둡니다. `I(1)=1일, I(2)=6일, n>2이면 I(n)=I(n−1)×EF`. 응답 품질 q(0~5)로 `EF' = EF + (0.1 − (5−q)×(0.08 + (5−q)×0.02))`를 계산하고, EF는 1.3 밑으로 내려가지 않습니다(q=4면 EF 변화 없음). **q<3이면 EF는 그대로 두고 반복을 처음(I(1))부터** 다시 시작합니다. 그날 복습이 끝난 뒤 q<4인 문항은 한 번 더 풉니다. | [S2](추정) |
| HLR(Duolingo) | 2016년 ACL 논문(Settles & Meeder). 단어마다 반감기 h를 학습 데이터(1,300만 학습 기록)로 회귀해 `p = 2^(−Δ/h)`를 예측합니다. 오차가 Leitner 방식의 절반 수준이고, 실서비스 A/B 테스트에서 연습 세션 유지율 +9.5%, 레슨 +1.7%, 전체 활동 +12%였다고 합니다(수치는 검색 요약, **추정**). | [S6], [S7](추정) |
| FSRS | 난이도 D(1~10), 안정도 S(회상 확률이 90%가 되는 간격), 회상 가능성 R로 기억을 모델링합니다. 최신 FSRS-6은 파라미터 21개, 망각 곡선 `R(t,S) = (1 + factor·t/S)^(−w20)`(R(S,S)=0.9가 되도록 factor 결정)이고, 목표 유지율 r에 맞춰 다음 간격 `I = S/factor · (r^(1/−w20) − 1)`을 구합니다. 평가는 Again/Hard/Good/Easy 4단계입니다. 파이썬 구현(py-fsrs)의 기본값은 목표 유지율 0.9, 학습 단계 1분·10분, 재학습 단계 10분, 최대 간격 36,500일, 간격 흔들기(fuzzing) 켜짐입니다. Anki 사용자 1만 명·리뷰 약 7.27억 건 벤치마크에서 FSRS-6의 log loss는 0.3460, HLR은 0.4694입니다(낮을수록 좋음). SM-2의 벤치마크 순위는 **미확인**입니다. | [S3], [S4], [S5] |

**PyRpg에 주는 의미**: FSRS가 예측은 가장 정확하지만, 파라미터를 학습하려면 사용자당 많은 리뷰 기록이 필요합니다. PyRpg의 그림자 몬스터는 학습자 1명이 수십~수백 개 정도만 만들 것이므로(**추정**), **고정 간격 Leitner 변형**이 단순하고 학습자에게 설명하기도 쉽습니다. 다만 SM-2의 "I(1)=1, I(2)=6" 같은 초반 간격과, HLR식 "틀려도 첫 칸까지는 안 떨어뜨리는" 완만한 강등을 섞어 씁니다.

### 1.9 그림자 몬스터 간격 반복 방식(제안)

**설계 방향**: 고정 간격 Leitner 변형을 씁니다. 첫 간격은 SM-2처럼 1일로 시작하고, 강등은 원래 Leitner처럼 첫 칸으로 리셋하지 않고 HLR 기준선처럼 완만하게 내립니다. 숫자는 출처의 알고리즘을 참고한 **제안값**입니다.

#### 등록 조건(design.md §5.3과 연결)

- 힌트 2단계 이상 사용, 해설서 열람, 같은 적에게 HP 0(쓰러짐) 1회 이상 → 해당 문제의 **개념**을 그림자 몬스터로 등록합니다.
- 등록 위치: 해설서 열람 → 칸 0, 쓰러짐·힌트 2~3단계 → 칸 1.
- 같은 개념이 이미 등록되어 있으면 새로 만들지 않고, 현재 칸에서 강등 규칙을 적용합니다.

#### 칸과 간격

| 칸 | 다음 출현까지 | 비고 |
|---|---|---|
| 0 | 1일 | 해설서를 본 개념. 다음 날 바로 다시 만납니다. |
| 1 | 1일 | SM-2의 I(1)=1일 [S2] |
| 2 | 3일 | |
| 3 | 7일 | SM-2의 I(2)=6일 [S2]과 비슷한 위치 |
| 4 | 14일 | |
| 5 | 30일 | 통과하면 **정화**(졸업). 코덱스에 '정화된 그림자'로 수집됩니다. |

#### 판정과 이동 규칙

| 결과 | 이동 | 이유 |
|---|---|---|
| 힌트 없이, 3회 시전 안에 AC | 한 칸 승급 | |
| 힌트 1단계만 쓰고 AC, 또는 4회 이상 시전 후 AC | 칸 유지(간격 다시 시작) | SM-2의 q=3(맞혔지만 어려움)처럼 통과는 인정하되 간격은 늘리지 않습니다 [S2] |
| 힌트 2~3단계를 쓰고 AC | 한 칸 강등(최소 칸 1) | HLR 기준선의 "틀리면 간격 절반" [S6] |
| 해설서 열람, 또는 HP 0으로 후퇴 | **두 칸** 강등(최소 칸 0) | 원래 Leitner의 "첫 칸 리셋"은 칸 5에서 실패했을 때 너무 가혹합니다 [S1](추정) |
| 칸 5에서 정화된 뒤 | 90일 뒤 1회 '귀환 그림자' 출현(선택). 통과하면 끝, 실패하면 칸 3으로 | FSRS 최대 간격 기본값은 매우 길지만(36,500일) [S4], 코딩테스트 준비 기간을 고려해 1회만 확인합니다 |

#### 하루 운영 규칙

- **하루 출현 상한 3마리.** 하루 15~30분 중 복습에 5~10분만 쓰게 하려는 값입니다(제안값).
- 출현 대상이 상한보다 많으면 **연체일이 긴 것 → 칸이 낮은 것** 순서로 고르고, 나머지는 다음 날로 넘깁니다. 넘어간 몬스터에는 벌칙이 없습니다(밀린 복습이 쌓여 압박이 되는 것을 막기 위함).
- 연체된 몬스터를 통과해도 칸 이동은 위 규칙 그대로입니다(오래 버틴 것을 별도로 보너스 주지 않음, 단순성 우선).
- 그림자 몬스터는 **원래 문제와 같은 개념의 변형 문제**로 나옵니다(입력값·스토리만 바꾼 문제 2~3개를 돌려 씀). 답 자체를 외워서 통과하는 것을 막기 위해서입니다.
- 보상: 원래 전투 보상의 50% XP와 골드. 그림자 1마리 처치도 스트릭 인정 조건(권고 #5)에 포함합니다.
- 같은 날 칸 0에서 실패한 몬스터는 다시 내지 않습니다(같은 날 반복은 SM-2의 "q<4 재복습"과 비슷하지만, 하루 학습 시간을 지키기 위해 생략).

#### 나중에 바꿀 수 있는 지점

- 플레이 기록(칸별 통과율)이 쌓이면, 칸 4·5의 통과율이 90%를 크게 넘을 때 간격을 늘리고, 크게 밑돌 때 줄입니다. FSRS도 목표 유지율 0.9를 기본으로 삼습니다 [S4].
- 기록이 충분히 많아지면 py-fsrs로 바꿀 수 있도록, 시도마다 `개념ID, 날짜, 결과(Again/Hard/Good/Easy에 대응)`를 저장해 둡니다. 결과 매핑 제안: 해설서/후퇴 = Again, 힌트 2~3단계 = Hard, 힌트 1단계·4회 이상 = Good, 힌트 없이 3회 안 = Easy.

### 1.10 피해야 할 함정

1. **스트릭이 목적이 되는 것**: Duolingo 사례처럼 숫자 유지가 학습보다 앞서고, 긴 스트릭이 끊기는 순간이 이탈 계기가 됩니다 [D5](추정). → 주간 지표 우선(권고 #8), 보호 장치 2개, 복구 경로.
2. **모호한 힌트와 난이도 급상승**: Codédex와 CodeCombat 모두 같은 비판을 받습니다 [C4][CC9](추정). → 지역마다 같은 개념의 쉬운 연습 전투를 최소 1개 두고, 시간 기반 우회(권고 #10)로 연결.
3. **게임 요소가 학습을 가리는 것**: CodeCombat에는 "코딩을 배우는 건지 게임을 하는 건지 모르겠다"는 학부모 의견이 있습니다 [CC9](추정). → 장비·꾸미기 보상은 편의 요소에 한정하고, 전투 결과는 항상 코드 실행 결과로만 결정.
4. **밀린 복습 더미**: 간격 반복은 하루라도 쉬면 출현 대상이 쌓입니다. → 하루 상한 3마리와 벌칙 없는 이월.
5. **답 암기**: 같은 문제를 반복 출제하면 이해가 아니라 정답을 외웁니다. → 변형 문제 풀(2~3개)을 돌려 씀.
6. **보상 인플레이션**: 상자, 물약, 보너스가 늘면 XP 숫자가 의미를 잃습니다. Boot.dev도 Potion 효과를 줄였습니다 [B9]. → XP 배율 아이템은 넣지 않거나, 넣더라도 그림자 몬스터에는 적용하지 않음.
7. **시작 장벽**: TwilioQuest처럼 로컬 Python 설치를 요구하면 첫날 이탈이 생깁니다(추정) [T4]. → PyRpg는 Pyodide로 브라우저 안에서 바로 실행(§0 #3과 같은 방향).

### 1.11 미확인으로 남은 항목

- Codédex의 공식 페이지 본문(프록시 차단으로 검색 요약만 확인), 스트릭 보호 장치, 힌트·해답 비용, 레벨 10 이상 XP 표
- CodeCombat의 레벨별 XP·젬 보상 크기, AI 크레딧 수, 현재 구독 가격(서버 데이터 또는 공식 페이지 차단)
- TwilioQuest 엔진의 레벨 공식, 스트릭 유무, 현재 배포 상태
- Duolingo 블로그 원문(프록시 차단으로 검색 요약만 확인), SM-2 EF 초깃값, srs-benchmark에서 SM-2의 순위

**PyRpg에 주는 영향과 권고**

- 게임에서 안내하려던 백준 링크(`https://www.acmicpc.net/problem/{번호}`)는 현재 열리지 않습니다. 재개 후에도 같은 번호와 주소가 유지되는지는 **미확인**입니다.
- 권고 1: 문제 데이터에는 백준 문제 번호만 저장하고, URL은 설정값(base URL)과 조합해서 만듭니다. 재개 후 도메인이 바뀌어도 한 곳만 고치면 됩니다.
- 권고 2: 백준이 재개되기 전까지는 프로그래머스 문제의 비중을 높이거나, 백준 문제는 번호와 제목만 안내하고 링크는 비활성으로 둡니다.
- 권고 3: solved.ac 티어는 BOJ 연동이 끝난 2026-04-28 시점 이후로 갱신되지 않았을 수 있습니다(**추정**).
- 백준식 stdin/stdout 문제 형식 자체는 그대로 연습할 가치가 있습니다. 다른 채점 사이트와 기업 코딩테스트에서도 같은 형식을 쓰기 때문입니다(**추정**: 이 문장은 이번 조사에서 출처로 확인하지 않았습니다).

**결론(2.3)**: 국내 코딩테스트에서는 **구현·시뮬레이션, 그래프 탐색, 완전탐색**이 세 자료(공식·준공식·개인)에서 공통으로 가장 많이 나옵니다. 프로그래머스 Kit(공식)는 구현·시뮬레이션과 문자열 카테고리를 두지 않지만, 준공식 도서 두 권은 모두 '구현' 장을 따로 둡니다. 따라서 PyRpg 커리큘럼에 구현·시뮬레이션을 명시적으로 다루는 지역(또는 보스전)이 필요하다는 근거가 됩니다.

#### 2.4.2 재귀 한도

| 항목 | 내용 | 근거(신뢰도) |
|---|---|---|
| 기본 한도 | `sys.getrecursionlimit()` = **1000** (CPython 3.11.15, 3.13.14 모두). 깊이 1500 재귀에서 `RecursionError: maximum recursion depth exceeded` | **직접 측정** |
| `setrecursionlimit` 공식 설명 | "인터프리터 스택의 최대 깊이를 설정한다. 가능한 최대값은 플랫폼에 따라 다르며, 너무 높게 잡으면 크래시가 날 수 있다." | Python 3.13/3.14 `Doc/library/sys.rst`(**공식**) |
| 3.12 변경 | "재귀 한도는 이제 Python 코드에만 적용된다. 내장 함수는 재귀 한도를 쓰지 않고 다른 메커니즘으로 보호된다." | Python 3.12 What's New(**공식**) |
| 깊은 재귀 실측 | `setrecursionlimit(10**6)` 후 깊이 999,900까지 3.11, 3.13 모두 정상 종료(스택 ulimit 8 MB 환경). 깊이 10만 재귀의 최대 RSS ≈ 21~22 MB(기본 7~8 MB) | **직접 측정**. 채점 서버의 스택·메모리 제한은 미확인이므로 "로컬에서 됐다 = 채점에서 된다"는 아님 |
| 흔한 실패 | ① 한도를 안 올려 `RecursionError`(런타임 에러) ② 너무 깊어 스택 부족으로 SIGSEGV ③ 메모이제이션 없는 중복 재귀로 시간 초과 | 검색 요약(인프런 Q&A 등, 개인 / 추정) + 공식 문서 경고 |
| PyRpg 권고 | 재귀 지역(6)에서 1000 한도를 체험시키고, 그래프 지역(12)에서 "재귀 DFS → 스택 반복 DFS" 전환을 보스 요건으로 둡니다. Pyodide의 재귀 한계는 별도 조사(§3 기술 조사) 필요 | 판단 |

#### 2.4.3 입출력 속도(직접 측정, 정수 10⁶개, 3회 중 최소값)

| 방식 | CPython 3.11 | CPython 3.13 |
|---|---|---|
| `input()` 10⁶번 | 0.58 s | 0.67 s |
| `sys.stdin.readline` 10⁶번 | 0.15 s | 0.20 s |
| `sys.stdin.buffer.read().split()` 한 번에 | 0.15 s | 0.13 s |
| `print(i)` 10⁶번 | 0.66 s | 0.81 s |
| `sys.stdout.write('\n'.join(...))` 한 번 | 0.16 s | 0.12 s |

→ 입력은 `input()` 대비 `sys.stdin.readline`이 **약 3~4배**, 출력은 `print` 반복 대비 `join` 한 번이 **약 4~7배** 빠릅니다(stdout은 /dev/null로 버림. 실제 파이프에서는 차이가 더 날 수 있음, 추정). `readline`은 줄바꿈 문자를 포함하므로 문자열 입력 시 `.rstrip()`이 필요합니다.

#### 2.4.4 시간 초과(TLE)·메모리 초과(MLE)·오답의 흔한 원인

| 분류 | 원인 | 실측/근거 | 대안 |
|---|---|---|---|
| TLE | `input()`·`print()`를 10⁵회 이상 반복 | 위 2.4.3 | `sys.stdin.readline`, `'\n'.join` |
| TLE | `list.pop(0)`로 큐 구현 | 10⁵개: **0.80 s** vs `deque.popleft` **0.007 s**(약 100배) | `collections.deque` |
| TLE | `x in list` 반복 | 길이 10⁴ 리스트에 10⁴번: **0.30 s** vs set **0.0004 s** | `set`/`dict` |
| TLE | O(n²) 알고리즘(이중 반복, 매번 정렬, 슬라이싱 복사) | 일반론 | 정렬+이분탐색, 누적합, 투 포인터 |
| TLE | 메모이제이션 없는 중복 재귀 | 검색 요약(추정) | `functools.lru_cache`, 바텀업 DP |
| 런타임 에러 | 재귀 한도 1000 초과 | 2.4.2 | `setrecursionlimit` 또는 반복문 |
| 런타임 에러 | **4300자리 초과 정수 ↔ 문자열 변환**: `int('9'*5000)`, `str(10**5000)` 모두 `ValueError: Exceeds the limit (4300 digits)` | **직접 측정**(3.11, 3.13). `sys.get_int_max_str_digits()`는 3.11에서 추가(공식 문서) | 큰 수 출력 문제에서 `sys.set_int_max_str_digits(0)` |
| MLE | 서로 다른 int 10⁶개 리스트 ≈ **40 MB**, `[0]*10**6` ≈ **8 MB** | **직접 측정**(tracemalloc) | 필요한 크기만, 비트/배열 재사용, 제너레이터 |
| MLE | 깊은 재귀의 프레임 누적 | 2.4.2(깊이 10⁵에 +14 MB) | 반복문 |
| 오답 | `[[0]*m]*n`은 같은 행 객체를 공유 → 한 칸 수정이 모든 행에 반영 | **직접 측정**: `[[1,0,0],[1,0,0],[1,0,0]]` | `[[0]*m for _ in range(n)]` |
| 오답 | `readline`의 `\n` 미제거로 문자열 비교 실패 | 일반론 | `.rstrip()` / `.split()` |

**PyRpg 반영 제안**: 지역 7(성능 습관) 보스전에 위 표의 `pop(0)`, `in list`, `input()` 반복을 "함정 몬스터"로 넣고, 테스트 입력 크기를 위 실측 배율이 드러나는 10⁵~10⁶으로 잡습니다(Pyodide 속도 배율은 §3 기술 조사에서 확인 필요). 4300자리 제한은 지역 1(형변환) 또는 정수론 지역의 "숨은 함정"으로 쓸 수 있습니다.

## 3. 기술 조사

### 3.1 Pyodide 버전과 크기(조사 완료)

- npm dist-tags(https://registry.npmjs.org/pyodide 조회): `latest` = **314.0.7**(2026-09-14), `stable-0.29` = **0.29.5**(2026-09-16), `stable-0.27` = 0.27.8, `next` = 315.0.0-alpha.2입니다. 즉 **유지보수 중인 라인이 두 개**입니다.
- 버전 번호 체계가 바뀌었습니다. 0.29.x 다음 버전이 314.0.0(2026-06-09)이며, 314.0.0의 changelog에는 "Upgraded to Python 3.14.2"와 "ABI Break Upgraded Emscripten to 5.0.3"이 적혀 있습니다. (https://pyodide.org/en/stable/project/changelog.html)
- 라인별 CPython 버전(npm tarball 안 `pyodide-lock.json`의 `info.python` 값으로 확인):
  - 314.0.7 → Python 3.14.2, Emscripten 5.0.3
  - 0.29.5 → Python 3.13.2, Emscripten 4.0.9
- 314.0.0의 주요 breaking change(changelog 원문 기준):
  - `pyodide.asm.js`의 이름이 `pyodide.asm.mjs`로 바뀌었고, "Classic (non-module) workers: No longer supported"라고 명시되어 있습니다. 따라서 Web Worker를 module worker로 만들어야 하고, 번들러 설정도 새 파일명을 참조해야 합니다.
  - 표준 라이브러리 분리 배포(unvendor)를 중단해서 `sqlite3`, `lzma`가 기본 포함됩니다. `ssl`은 stub이 되었고, OpenSSL 기반 `hashlib` 해시가 제거되었습니다.
  - `pyodide.ffi.JsBigInt`가 추가되었습니다. JS와 Python 사이의 큰 정수 변환 규칙은 아직 조사하지 못했습니다(**미확인**).
- 코어 다운로드 크기(**직접 측정**: npm tarball의 파일 크기와 `gzip -9` 결과):

  | 파일 | 314.0.7 원본 | 314.0.7 gzip | 0.29.5 원본 | 0.29.5 gzip |
  |---|---|---|---|---|
  | pyodide.asm.wasm | 9.60 MB | 3.54 MB | 8.65 MB | 2.83 MB |
  | pyodide.asm.mjs(0.29는 .js) | 1.25 MB | 0.26 MB | 1.07 MB | 0.22 MB |
  | python_stdlib.zip | 2.55 MB | 2.50 MB | 2.42 MB | 2.38 MB |
  | pyodide.mjs + pyodide-lock.json | 0.14 MB | 0.03 MB | 0.14 MB | 0.03 MB |
  | **합계(코어)** | **약 13.5 MB** | **약 6.3 MB** | **약 12.3 MB** | **약 5.5 MB** |

  `python_stdlib.zip`은 이미 압축된 파일이라 gzip으로 거의 줄지 않습니다.
- 공식 문서에 따르면 전체 배포판은 "200+ megabytes"이고, 최소 실행 파일 묶음인 pyodide-core는 "npm install pyodide를 했을 때 설치되는 파일과 같은 묶음"입니다. (https://pyodide.org/en/stable/usage/downloading-and-deploying.html)

**버전 선택 검토 포인트(미결정)**: 0.29 라인은 Python 3.13이라서, 샘플 문제를 검증한 로컬 CPython 3.13.3과 minor 버전이 같습니다. 314 라인은 최신이지만 큰 breaking change를 막 겪은 버전입니다. '안정성 우선' 원칙에 비춰 보면 0.29 라인이 유력하지만, 0.29 라인의 지원 종료 시점을 확인한 뒤에 design.md §9에서 결정합니다.

### 3.2 미착수 항목

- Pyodide: Vite 로컬 번들 방법, Web Worker 패턴, `setStdin`·`setStdout` 시그니처, 무한루프 처리(`worker.terminate()`와 interrupt buffer 비교, COOP/COEP 헤더), CPython 대비 속도, 재귀 깊이 한계, 메모리와 큰 정수, 테스트별 전역 상태 격리, JS↔Python 큰 정수 변환
- 게임 엔진(Phaser 3/4 상태와 대안), CodeMirror 6(한글 IME 포함), 저장 방식, Tiled/LDtk, CC0 에셋과 한국어 픽셀 폰트, Electron/Tauri 제약, Playwright로 canvas 게임 테스트
