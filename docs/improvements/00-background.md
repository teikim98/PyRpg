# 개선안 작성 경위

> 작성: 2026-10-15. 이 폴더의 개선안이 어떤 과정을 거쳐 만들어졌는지 기록합니다.
> 개선안 본문은 [README.md](./README.md)부터 읽습니다.

## 1. 출발점

2026-10-15에 사용자가 "지금까지 기획한 내용을 외부 모델(Gemini)에게 검증받고 싶다"고 요청했습니다. 코드 수준이 아니라 기획 단계의 문서를 대상으로 하는 검증이었습니다.

검증의 초점은 사용자가 직접 정했습니다. 도트 아트나 기술 스택이 아니라 **게임의 진행 방식과 레벨 디자인**을 본다는 것입니다. 구체적으로는 다음 세 가지 질문입니다.

1. 사용자가 게임을 재미있게 플레이할 수 있는가?
2. 플레이를 통해 실제로 코딩테스트 실력을 얻어 갈 수 있는가?
3. 점점 어려워지지만, 앞의 과제를 통과했다면 다음 과제를 충분히 진행할 수 있는가?

## 2. Gemini 검토 방식

- **모델**: Vertex AI의 `gemini-4-argon`을 썼습니다(thinkingLevel HIGH). 관점 A·B에서는 웹 검색 도구(`googleSearch`)도 켰습니다.
- **관점 4개**: 하나의 질문에 모든 것을 묻지 않고, 관점마다 따로 질문했습니다.

| 관점 | 질문 | Gemini에 보낸 자료 |
|---|---|---|
| A. 재미·몰입 루프 | 하루 15~30분 학습을 수개월 동안 계속 하고 싶게 만드는가? | 첫 프롬프트, design.md, research.md, progress.md |
| B. 실력 전이 | 게임을 끝내면 백준 실버~골드, 프로그래머스 Lv.2~3 수준에 도달하는가? | 첫 프롬프트, design.md, research.md, 지역 1~4 명세 |
| C. 미시 난이도 곡선 | 지역 1~4의 실제 문제가 앞에서 배운 것만으로 풀리는가? | design.md, phase3/plan.md, 지역 1~4 명세, 지역 1~3 실제 레슨·문제 요약본 |
| D. 거시 레벨 디자인 | 17개 지역 전체의 순서, 난이도 벽, 분량과 페이스가 적절한가? | 첫 프롬프트, design.md, research.md, phase3/plan.md, progress.md |

- **사용량**: 4번의 호출 모두 첫 시도에 성공했습니다. 한 번에 4~9분이 걸렸고, 토큰은 합계로 입력 338,189, 출력 41,387, thinking 66,425입니다.
- **대조 단계**: Gemini의 응답을 그대로 받아들이지 않았습니다. Claude 서브에이전트가 관점을 하나씩 맡아서, Gemini가 지적한 내용마다 실제 문서·콘텐츠·코드를 열어 확인했습니다. 판정은 다섯 가지(타당 / 부분 타당 / 이미 반영됨 / 오독·사실 오류 / 판단 보류)였습니다. 긴 문서를 읽은 모델은 이미 있는 내용을 "빠졌다"고 하거나 절 번호를 잘못 인용할 수 있기 때문에 이 단계를 두었습니다.

## 3. Gemini 검토 결과 요약

### 판정 집계

| 관점 | 타당 | 부분 타당 | 이미 반영됨 | 오독 | 보류 | 계 |
|---|---|---|---|---|---|---|
| A | 3 | 5 | 0 | 0 | 0 | 8 |
| B | 7 | 5 | 0 | 1 | 1 | 14 |
| C | 7 | 10 | 1 | 0 | 2 | 20 |
| D | 3 | 6 | 0 | 0 | 0 | 9 |
| **계** | **20** | **26** | **1** | **1** | **3** | **51** |

"부분 타당"이 절반을 넘었습니다. 대부분은 Gemini가 이미 있는 완충 장치(필수·선택 전투 구분, 주간 스트릭, 보호 장치 등)를 빼고 계산해서 영향을 과장한 경우였습니다. 그래서 개선안은 Gemini의 결론을 그대로 옮기지 않고, 문제의식만 취한 뒤 해결책을 다시 설계했습니다.

### 확인된 핵심 문제

1. **유형 판별 훈련이 없습니다**(A·B·D 공통). 레슨 비석 바로 뒤의 몬스터가 그 주문서를 요구하므로, 몬스터를 만나는 순간 쓸 개념이 드러납니다. design.md §7.1에 정의된 '응용 전투'는 지역 1~3에 하나도 없습니다. 실전에서 필요한 "문제를 보고 어떤 개념인지 알아내는 능력"을 기르지 못하는 구조입니다.
2. **복습이 다른 모양으로 적용하는 능력을 기르지 못합니다**(A·B·D). 그림자 몬스터의 변형은 숫자와 이야기만 바꾼 것이고, 게시판에 주문서 이름이 드러납니다. 보스의 핵심인 효율 개선(2페이즈)은 복습에서 다시 나오지 않습니다.
3. **선행 지식 역전이 있습니다**(B·C·D). P0302·P0303·P0309는 아직 배우지 않은 함수와 문법을 요구하고, P0308은 정답이 레슨 예제와 같습니다. 지역 1의 실전 추천 문제 6개 중 5개도 아직 배우지 않은 반복문이나 list를 요구합니다.
4. **막혔을 때 빠져나갈 장치가 비어 있습니다**(A·C·D). 연습 전투(`practice: true`)가 0개인데도 연습 제안 대사가 뜹니다. 해설서는 같은 적에게 세 번 쓰러져야 열리고, 지역 17 졸업 시험은 규칙이 정해져 있지 않습니다.
5. **후반의 분량과 페이스가 맞지 않습니다**(A·B·D). 지역 16은 알고리즘 5종을 일반 전투 12개로 다루고, 출제 빈도가 높은 구현·시뮬레이션(지역 13)도 분량이 적습니다.
6. **재미 요소에 빈틈이 있습니다**(A). 골드를 쓸 곳이 거의 없고, 상점은 에코 마을 한 곳뿐이며, 기획서의 맵 퍼즐은 구현되어 있지 않습니다.

### Gemini가 틀렸거나 과장한 것

대조 단계가 없었다면 그대로 반영되었을 수 있는 지적들입니다.

- "에디터 자동완성이 켜져 있다": 사실이 아닙니다. `src/ui/editor.ts`에는 자동완성 확장이 없습니다.
- "그림자 변형 규칙은 자기모순이다": design.md §7.6이 변형을 처음부터 "입력값과 이야기만 바꾼 것"으로 정의했다는 점을 놓쳤습니다.
- "지역 8의 `list.pop(0)` 풀이가 시간 결계를 통과해 버린다": research.md의 측정값(`deque`와 약 100배 차이)과 맞지 않습니다.
- "최종 도달 수준은 백준 브론즈 1~실버 3": 지역 8~16의 보스와 추천 문제가 골드 하위를 겨냥한다는 점을 반영하지 않은 과소 추정입니다.
- 전체 기간 "4~5개월": 실측값과 주 5일 기준으로 다시 계산하면 8~11개월입니다(추론).

## 4. 개선안 작성 과정

Gemini 검토 결과를 사용자와 함께 살펴본 뒤, 사용자가 "이것을 토대로 기획서의 개선안을 만들어 달라"고 요청했습니다. 이때 개선안 작성 자체에는 Gemini를 다시 호출하지 않고, Claude 에이전트가 직접 작업하기로 했습니다.

1. **영역별 작성(에이전트 4개, 병렬)**: 위의 핵심 문제를 네 영역으로 나누었습니다. 에이전트마다 한 영역을 맡아 Gemini 대조 결과를 출발점으로 삼고, 실제 문서·콘텐츠·코드를 다시 확인한 뒤 개선안을 썼습니다. 모든 개선안은 "현상 → 원인 → 대안 비교 → 추천안 → design.md 변경 초안 → 영향 범위 → 작업량" 형식을 따릅니다.
   - ① 실력 전이(핵심 문제 1, 2)
   - ② 선행 지식 보장(핵심 문제 3). 지역 1~4의 42문제에 AST 기반 선행 지식 검사 프로토타입을 실제로 돌려서 설계의 실효성을 확인했습니다.
   - ③ 막힘 탈출과 졸업 시험(핵심 문제 4)
   - ④ 페이스와 보상(핵심 문제 5, 6). 지역 1~4의 실측값으로 전체 기간을 다시 계산했습니다.
2. **통합 점검(에이전트 1개)**: 네 에이전트는 서로의 결과를 보지 못한 채 작업했으므로, 마지막에 한 에이전트가 네 문서를 함께 읽고 점검했습니다.
   - 충돌과 빈틈 23건을 찾아서 통합 결정을 내렸습니다. 예를 들어 ①은 응용 전투를 기존 전투 안에서 지정했는데 ④는 응용 전투를 추가 전투로 계산했고, ①의 '실전 시계'와 ③의 '소프트 타이머'는 같은 장치였습니다.
   - 네 문서의 사실 주장 16건을 표본으로 다시 확인했고, 그중 틀린 4건을 고쳤습니다.
   - 네 문서에서 모인 사용자 결정 사항 약 30개를 시점별로 나누었습니다. 지금 정해야 하는 것은 5개이고, 나머지는 추천안을 기본값으로 둡니다.

작성 원칙은 다음과 같습니다.

- design.md를 비롯한 기존 문서와 코드는 수정하지 않았습니다. 개선안은 이 폴더에만 있습니다.
- 1인 개발자가 남은 지역 13개를 만들어야 한다는 점을 고려해서, 콘텐츠를 새로 많이 만들지 않는 안을 우선했습니다. 네 개선안 모두 새 문제는 거의 0개이고, 기존 문제와 변형을 다시 쓰는 방식입니다.
- 새 라이브러리는 제안하지 않았습니다.
- 확인한 사실과 추론을 구분하고, 추론에는 "(추론)"을 붙였습니다.

## 6. 원자료의 위치

Gemini 검토의 원자료는 저장소 루트의 `gemini/` 폴더에 있습니다. 이 폴더는 **로컬에만 있고 커밋하지 않았습니다.** 그래서 개선안 본문에 있는 `gemini/종합.md`, `gemini/verified/*.md` 같은 참조는 원격 저장소에서 열리지 않습니다. 이 문서의 §3이 그 내용을 대신 요약합니다.

| 경로 | 내용 |
|---|---|
| `gemini/review.mjs` | Vertex AI 호출 스크립트 |
| `gemini/prompts/` | 관점별 질문과 공통 검토 원칙 |
| `gemini/raw/A~D.md` | Gemini 응답 원문과 토큰 사용량 |
| `gemini/verified/A~D.md` | 지적별 대조 결과와 판정 |
| `gemini/종합.md` | 4개 관점의 종합 |
