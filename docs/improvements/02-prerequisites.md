### 3.1 L4-3에 서식이 몰린 문제

**현상**: 명세 31행은 L4-3에 `split` 두 형태, `join`, `list(s)` → `join`, 서식 5종을 몰아 둡니다. 문제에서 쓰는 서식은 P0406의 `{x:,}`와 P0408의 `{avg:.2f}`뿐입니다(43~45행). 콘텐츠 브랜치의 L4-3은 이미 `list(s)` → `join`을 독립된 절로 두었지만(브랜치 `L4-3/lesson.md:34-45`), 정렬·0 채우기 서식 세 줄은 그대로 들어 있습니다(57~60행, summary에도 있음).

**명세 변경 초안**(31행 '다루는 내용' 열을 교체):

> `split()`(공백 여러 개)과 `split(',')`(빈 문자열이 생김), `'구분자'.join(리스트)`(원소가 문자열이어야 함), **`list(s)` → 고치기(두 칸 맞바꾸기 `a[i], a[j] = a[j], a[i]` 포함) → `''.join`을 독립된 절로**, f-string 서식은 문제에서 쓰는 `{x:.2f}`, `{x:,}`만 예제로 두고 `{x:>5}`·`{x:<5}`·`{x:05d}`는 "이런 서식도 있다"는 한 문장으로 줄입니다.

**구현 브랜치 영향**: 브랜치 `-1`의 `content/regions/r04-grand-library/lessons/L4-3/lesson.md`(57~60행의 `n = 42`와 세 서식 줄을 빼고 한 문장으로 바꾸며, 44행 뒤에 맞바꾸기 두 줄 추가)와 같은 폴더의 `lesson.json`(summary에서 세 서식 제거). 테스트와 변형은 바뀌지 않습니다. 브랜치의 `tests/unit/content-r04.test.ts`는 레슨의 주문서 ID만 확인하므로(21~22행) 영향이 없습니다.

**현상**: 명세 41행은 "앞뒤 공백 제거, 소문자, 공백 → `-`"만 적었습니다. 단어 사이 공백이 여러 칸이면 `replace(" ", "-")`와 `"-".join(s.split())`의 답이 달라집니다. 콘텐츠 브랜치는 지문 제한에 "단어 사이의 공백은 한 칸입니다(앞뒤에는 공백이 여러 칸 있을 수 있음)"를 이미 넣었고, 테스트 입력도 그 조건을 지킵니다(브랜치 `P0404/problem.json`의 args를 모두 확인).

## 4. 선행 지식 자동 검사 설계

### 왜 필요한가

- 지역 2·3·4 명세는 모두 "지역 1~N 개념만 씁니다"라는 규칙을 둡니다(`region02-spec.md:42`, `region03-spec.md:43`, `region04-spec.md:50`). 그런데 이번에 찾은 정답 역전(P0302, P0303, P0309)은 **모두 같은 지역 안**에서 생겼습니다. 규칙의 단위가 지역이라서 이 규칙을 지켜도 막을 수 없었습니다.
- 지역 5~17은 지역마다 문제가 12~16개로 늘어나고, 사람이 레슨 순서와 모범답안을 하나씩 대조하는 비용도 커집니다. 검증 결과 에이전트가 지역 1~3을 손으로 대조해서 찾은 것을 콘텐츠를 만들 때마다 기계가 확인하게 하는 것이 목적입니다.
- **AST(추상 구문 트리)**는 코드를 "함수 호출", "for 문", "슬라이스"처럼 문법 단위의 나무로 바꾼 것입니다. 문자열 검색으로 `sum(`을 찾으면 주석, 문자열, 변수 이름 `summary(` 안의 글자까지 걸리지만, AST로는 "실제로 내장 함수 `sum`을 호출하는 곳"만 정확히 셀 수 있어서 필요합니다. Python 표준 라이브러리의 `ast`로 충분하고, `verify_content.py`는 이미 `ast`를 가져와 `literal_eval`에 쓰고 있습니다(22행). 새 라이브러리는 필요하지 않습니다.

**예시**(§1.1 반영 후의 L3-1):

```json
{
  "id": "L3-1",
  "title": "줄 세우기의 주문: 리스트",
  "scroll": { "id": "scroll.list", "name": "줄 세우기의 주문서", "summary": "..." },
  "introduces": [
    "list-literal", "subscript", "neg-index", "subscript-store", "in", "not-in", "starred-call",
    "call:list", "call:sum", "call:max", "call:min"
  ],
  "exercise": { "...": "..." }

```

**태그 형식**: 접두어가 있는 이름 태그와 고정된 문법 태그 두 종류입니다.

| 종류 | 형식 | 예 |
|---|---|---|
| 내장 함수 호출 | `call:<이름>` | `call:sum`, `call:enumerate` |
| 메서드 호출 | `method:<이름>` | `method:append`, `method:split` |
| 모듈 사용 | `import:<모듈>`, `api:<점 경로>` | `import:sys`, `api:sys.stdin.readline` |
| 키워드 인자 | `kwarg:<이름>` | `kwarg:end`, `kwarg:reverse` |
| 연산자 | `op:<기호>` | `op://`, `op:%`, `op:**` |
| 문법 | 고정 이름 | `if`, `elif`, `for`(range 순회), `for-iter`(그 밖의 순회), `while`, `break`, `continue`, `nested-loop`, `listcomp`, `comp-if`, `slice`, `slice-step`, `subscript`, `neg-index`, `subscript-store`, `fstring`, `fstring-format`, `starred-call`, `unpack-assign`, `unpack-for`, `tuple-assign`, `subscript-unpack`(맞바꾸기), `in`, `not-in`, `chain-compare`, `and`, `or`, `not`, `augassign`, `list-literal`, `list-mult`, `def`, `return`, `lambda`, `dict-literal`, `set-literal`, `tuple-literal`, `dictcomp`, `setcomp`, `genexp`, `ternary`, `try`, `with`, `class`, `decorator` 등 |

### 검사 규칙

**학습 시점(문제를 만나는 순간 플레이어가 아는 것)**

| 안 | 정의 | 평가 |
|---|---|---|
| 가. `requires` 기준 | 이전 지역의 모든 레슨 + 같은 지역에서 `requires`가 가리키는 레슨 중 **가장 뒤 번호까지**의 레슨 | `requires`는 같은 지역 주문서만 쓸 수 있고(`verify_content.py:418-420`), 전투를 여는 열쇠라서 "적어도 이 레슨까지는 읽었다"가 보장됩니다. 지역 안의 앞 레슨들은 각 레슨 뒤 필수 길목 몬스터가 지켜 줍니다 |
| 나. 맵 단계 기준 | 맵 생성기 `STAGES`에서 그 몬스터에 닿는 단계까지 닿는 비석 | 가장 정확하지만 `STAGES`가 콘텐츠가 아닌 `tools/maps/build_rNN.py`에 있어 검증기가 맵 생성기 코드에 묶입니다 |
| 다. 지역 기준 | 그 지역 레슨 전부 | 지금 명세 규칙과 같습니다. 프로토타입으로 확인하면 이번에 찾은 정답 역전 5건이 모두 사라집니다. 쓸모가 없습니다 |
| 라. 문제마다 `after` 필드 | 작성자가 직접 적음 | 데이터가 늘고 맵과 어긋날 수 있습니다 |

**추천: 가.** 프로토타입에서 가와 나를 지역 1~4의 42문제 모두에 계산해 비교했고, 학습 시점이 한 문제도 다르지 않았습니다. 가는 "지역 안의 레슨 번호 순서 = 비석을 만나는 순서"를 전제로 하므로, 이 전제를 design.md §4.1에 적고 맵 생성기 쪽에서 비석 순서를 확인하는 단언을 하나 더하는 것을 선택 사항으로 둡니다(§작업량 표). 이 정의는 ①의 응용 전투(`requires`가 지역 주문서 전부, 마지막 비석 뒤 배치)와 보스에도 그대로 맞습니다.

**허용 목록 = 학습 시점까지의 `introduces` 합집합 + 그 문제의 시작 코드(`starter.py`)에서 뽑은 태그**

시작 코드는 플레이어가 화면에서 이미 본 코드이므로 그 문제에서만 허용합니다. 예를 들어 P0103·P0202의 `def solution`과 `return`, P0108의 `return [h, m, s]`(list 리터럴, 지문이 "리스트는 지역 3에서 배워요"라고 안내함), 지역 3 stdin 문제의 `import sys`와 `input = sys.stdin.readline`이 여기에 해당합니다. 시작 코드가 `def`를 주면 도우미 함수를 하나 더 만드는 것도 허용되는데, 이 정도는 위험이 작다고 판단합니다(추론).

**무엇을 검사하지 않는가(오탐을 줄이는 기준)**

- 이름, 상수, 단순 대입, `+`·`-`·`*`, 기본 비교(`==`, `<` 등), 괄호처럼 모든 레슨의 바탕이 되는 것은 태그를 만들지 않습니다.

- 모범답안만 봅니다. 모범답안이 우회 풀이를 쓰면(P0411의 임시 변수 맞바꾸기) 지문이 요구하는 더 자연스러운 문법이 레슨에 없어도 통과합니다.
- 프로토타입은 `import X`만 처리합니다. 지역 5의 `from collections import Counter`처럼 가져온 이름을 호출하는 경우는 `api:collections.Counter`로 태그하도록 넓혀야 합니다. 지역 6을 위해 함수가 자기를 부르는 `recursion` 태그도 필요합니다.
- 실전 추천 문제는 저장소에 풀이가 없어 검사할 수 없습니다(§2.1).
- 허용 목록은 사람이 적습니다. 목록이 틀리면 검사도 틀리므로, 레슨 코드 블록 검사가 목록과 레슨의 어긋남을 일부 잡아 주는 것에 의존합니다.

## 다른 개선안과의 연결

- **① 실력 전이**
  - ①이 고른 응용 전투 규칙("`requires`는 그 지역 주문서 전부, 마지막 비석 뒤에 배치")은 이 개선안의 학습 시점 정의와 그대로 맞습니다. 응용 전투의 학습 시점은 그 지역의 마지막 레슨까지가 되고, 섞는 이전 지역 개념은 이미 허용 목록에 있습니다. 만약 나중에 `requires`를 비우는 쪽으로 바뀌면 학습 시점을 계산할 수 없게 되므로, 그때는 이 검사의 정의를 함께 바꿔야 합니다(충돌 가능 지점).
  - ①의 그림자 출제는 같은 `concept`의 **이미 푼** 문제를 고르므로 학습 시점 문제가 생기지 않습니다. 구조가 다른 변형을 허용해서 변형마다 별도 모범답안을 두게 되면, 그 답안도 이 검사의 대상에 넣어야 합니다.
  - 이 개선안이 레슨 예제를 바꾸는 것(P0308·P0204·P0409)은 "레슨 예제를 옮겨 적기만 해도 풀린다"를 없애므로 ①의 전이 목표를 돕습니다.
- **③ 막힘 탈출·졸업 시험**
  - 새로 만들 연습 전투도 같은 주문서를 `requires`로 두면 학습 시점이 같으므로 이 검사를 그대로 받습니다.
  - 해설서(`explanation.md`)는 검사하지 않기로 했으므로, ③이 해설서 해금 조건을 완화해도 이 검사와 충돌하지 않습니다.
  - 지역 17은 학습 시점이 모든 레슨이므로 검사가 사실상 열려 있습니다.
