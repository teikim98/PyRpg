문자열은 칸을 바꿀 수 없으니까, **고칠 수 있는 글자 리스트**로 바꿔서 고치고 마지막에 한 번만 엮으면 돼.

- `arr = list(s)`는 `"book"`을 `['b', 'o', 'o', 'k']`로 만들어. 리스트는 `arr[i] = c`로 칸을 바꿀 수 있어.
- 명령은 `cmd = input().split()`으로 나눠. 번호는 1부터 세니까 `int(cmd[1]) - 1`로 칸 번호로 바꿔. 그대로 쓰면 N번째 글자에서 `IndexError`가 나고 나머지도 한 칸씩 밀려.
- `SET`은 `arr[i] = cmd[2]`, `SWAP`은 `arr[i], arr[j] = arr[j], arr[i]`(i = j여도 그대로라 안전해), `UPPER`는 `arr[i] = arr[i].upper()`(메서드가 돌려준 값을 다시 담기!).
- 다 고친 뒤 `"".join(arr)`로 문자열로 엮고, 그 문장에서 `isupper()`인 글자를 세. UPPER 명령 수를 세면 같은 칸을 두 번 UPPER하거나 `SET`이 대문자를 덮을 때 틀려.
- 문장은 `input().rstrip()`으로 읽어. 줄바꿈을 떼지 않으면 `list(s)`에 `\n`이 한 칸 들어가서 출력에 빈 줄이 생겨.
- `s[i] = c`처럼 문자열 칸에 바로 넣으면 `TypeError: 'str' object does not support item assignment`야. 글자 읽기의 주문에서 본 그 에러!

**왜 `s = s[:i] + c + s[i + 1:]`은 느릴까?**

- 답은 맞아. 하지만 명령 하나마다 앞부분 복사, 뒷부분 복사, 이어 붙이기로 **문장 전체(N글자)를 새로 베껴 써**. 명령이 Q개면 N × Q. 2페이즈에서는 15만 × 80만, 1200억 글자가 넘게 옮겨야 해.
- 리스트로 고치면 명령 하나가 칸 하나만 바꾸니까, 문장을 리스트로 바꾸고(N) 명령을 처리하고(Q) 한 번 엮으면(N) 끝이야. O(N + Q).
- 출력할 문장을 `out = ""`에 `out += c`로 한 글자씩 이어 붙이는 것도 이 결계는 통과하게 잡았어. 이 보스가 막는 건 '고칠 때마다 전체를 새로 만드는 것'이니까. 다만 함수 밖(맨 바깥 줄)에서 쓴 문자열 `+=`는 이어 붙일 때마다 지금까지의 문자열을 통째로 복사해서, 길어질수록 점점 느려져(O(N²)). 15만 글자에서는 아직 버티지만 모범답안보다 느려. (함수 안의 변수라면 Python이 제자리에서 늘려 줘서 빠르지만, 그런 차이에 기대기보다 `join`을 쓰는 게 마음 편해.) 조각을 리스트에 모아 `"".join`으로 한 번에 엮는 게 빠르고 파이썬다워.

**시간 결계의 예산은 이렇게 정했어.**

- 게임은 기기마다 기준 루프(반복 100만 번 + dict 연산 20만 번)를 재서 `ref`로 삼고, 시간 결계 제한을 `budgetUnits × ref × 1.5 + 50 ms`로 정해. 이 보스의 `budgetUnits`는 **45**야.
- 브라우저(Pyodide)에서 잰 값(ref ≈ 47 ms): 모범답안은 2페이즈의 가장 느린 입력에서 약 0.6초(ref의 약 13배)였어. 대부분이 명령 80만 줄을 읽고 나누는 시간이야. 문자열 `+=` 출력 풀이는 약 0.85초(ref의 약 18배). 제한은 ref의 약 68배(약 3.2초)라서 모범답안은 5배, `+=` 풀이도 3.5배 넘게 여유가 있어.
- `s[:i] + c + s[i + 1:]` 풀이는 11~13초가 걸려. 제한의 세 배를 줘도 못 들어와.
- 명령을 80만 개로 키운 이유: `+=` 풀이와 슬라이싱 풀이는 둘 다 글자를 베껴 쓰느라 느려지는데, `+=`는 문장 길이에만, 슬라이싱은 문장 길이 × 명령 수에 비례해. 명령이 많을수록 둘 사이가 벌어져서, 둘을 확실히 가를 수 있었어.
- 결론: **고칠 수 있는 그릇에 담아 고치고, 마지막에 한 번 엮기.** 문자열을 여러 번 고치거나 이어 붙일 일이 생기면 언제나 `list`와 `join`을 떠올려.
